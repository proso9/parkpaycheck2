## 1. 背景与目标

本工具（parkpaycheck_v2）部署在服务器上常驻运行，定时扫描停车场系统日志并检测异常车辆（出场不开闸且判定窗口内无支付结果下发）。现需新增功能：**把检测结果上传到 Cloudflare D1 数据库**，供另一个独立项目读取、展示并修改数据。

全链路使用 Cloudflare 免费计划（D1 + Workers 额度）。本仓库**只负责上传侧**，展示项目不在本仓库范围内。

## 2. 已确认的架构决策

以下四项已与需求方确认，开发时不要更改：

| # | 决策项 | 结论 |
| - | ------ | ---- |
| 1 | D1 接入方式 | **直接调 Cloudflare D1 REST API**（`POST /accounts/{account_id}/d1/database/{database_id}/query`），不部署 Worker，不引入第三方依赖（用标准库 `urllib.request` 实现） |
| 2 | 上传范围 | **仅异常记录**，即当前 CSV 输出的内容（`find_anomalies` 的结果，含入场时间、费用、可疑标记） |
| 3 | 同步策略 | **只插入新记录，永不覆盖**：`INSERT OR IGNORE` + 唯一去重键。已存在记录（含展示项目人工修改的 status/remark）完全不动 |
| 4 | 人工维护字段 | **处理状态（status）+ 备注（remark）**，由展示项目维护，本工具只写入默认值 |

## 3. 整体数据流

```
服务器（本项目常驻 + APScheduler 定时）
  → 定时扫描日志 → 现有检测逻辑（parse_log → find_anomalies，不变）
  → 扫描全部日志并输出 CSV → 汇总本轮异常记录 → 统一分批上传 D1（INSERT OR IGNORE 幂等）
  → 全部批次成功 → 才把本轮日志统一标记为"已处理"（写入 .processed.json）
  → 任一批失败 → 本轮均不标记，下一轮自动重新检测并重试（去重键兜底，不产生重复）
另一项目 → 用 API Token 访问同一 D1 库，读取展示、修改 status/remark
```

## 4. D1 表结构（最终版）

表由本工具在首次上传前自动创建（`CREATE TABLE IF NOT EXISTS`），无需手动初始化：

```sql
CREATE TABLE IF NOT EXISTS anomalies (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  log_date      TEXT NOT NULL,   -- 来源日志日期（取自文件名，如 2026-08-22）
  log_file      TEXT NOT NULL,   -- 来源日志文件名（如 system.2026-08-22.log）
  entry_time    TEXT,            -- 入场时间，全格式 YYYY-MM-DD HH:MM:SS，找不到为 NULL
  exit_time     TEXT NOT NULL,   -- 出场时间，全格式 YYYY-MM-DD HH:MM:SS
  car_number    TEXT NOT NULL,   -- 车牌（已归一化：去空格、转大写）
  fee           REAL,            -- 用户需支付费用，无关联费用为 NULL
  is_suspicious INTEGER NOT NULL DEFAULT 0,  -- 停车时间可疑标记（现 CSV 中的"异常"列）
  dedup_key     TEXT NOT NULL UNIQUE,        -- 去重键，见第 5 节
  status        INTEGER NOT NULL DEFAULT 0,  -- 0=未处理 / 1=已处理 / 2=误报（展示项目维护）
  remark        TEXT,                        -- 备注（展示项目维护）
  created_at    TEXT NOT NULL DEFAULT (datetime('now'))
);
```

注意事项：

- 日志内的时间只有 `HH:MM:SS`，**入库前必须用来源日志文件名中的日期补全**为 `YYYY-MM-DD HH:MM:SS` 全格式（文件名形如 `system.2026-08-22.log`，可复用 `parkcheck/output.py` 中的 `LOG_DATE_RE` 提取日期）。
- `entry_time` 为 `-` 时存 `NULL`；`fee` 为 `-` 时存 `NULL`。
- `status`、`remark` 本工具永远只写默认值（0 / NULL），**绝不在 UPDATE 中触碰这两个字段**——实际上本工具对已有记录不做任何 UPDATE。

## 5. 去重键定义（幂等核心）

```
dedup_key = sha256( "{log_file}|{exit_time}|{car_number}" ) 的十六进制摘要
```

- `log_file` 用文件名（不含目录），`exit_time`/`car_number` 与入库值完全一致。
- 同一辆车多次不开闸会生成多条记录（`exit_time` 不同），哈希输入含出场时间即可区分。
- 上传使用 `INSERT OR IGNORE`，重复上传被 SQLite 唯一约束静默忽略，天然幂等，重试安全。

## 6. 上传时机与重试语义（与"跳过已处理日志"的衔接）

现有功能：内容未变化的已处理日志记录在输出目录 `.processed.json`（见 `parkcheck/state.py`），再次运行时自动跳过。加入上传后，语义调整为（实现时改为**统一上传**，比本文原逐文件方案更契合每日定时场景，2026-08-30 与需求方确认）：

1. 上传开关**关闭**时：行为与现在完全一致，检测 → 输出 CSV → 逐文件标记已处理。
2. 上传开关**开启**时：**扫描全部日志 → 输出 CSV → 汇总本轮所有异常记录，统一分批上传 D1** → 全部批次成功后才把本轮所有日志 `state.mark()` 标记已处理。
3. 上传失败（网络断开、Token 无效、库 ID 错误等）：**本轮所有日志均不标记**，打印明确错误后结束本轮。下一轮定时触发时这些日志会被重新检测并重试上传，`INSERT OR IGNORE` 保证不产生重复数据。
4. 单条记录上传失败视为整批失败（本轮不上传成功，下轮重试）。
5. D1 限制：单次查询最多 100 个绑定参数，每行 8 个参数，单批最多 12 行；配置的批量大小超过时自动收紧。

## 8. Cloudflare D1 REST API 调用规格

- 端点：`POST https://api.cloudflare.com/client/v4/accounts/{account_id}/d1/database/{database_id}/query`
- 请求头：`Authorization: Bearer <API Token>`，`Content-Type: application/json`
- 请求体（参数化，防注入）：

```json
{
  "sql": "INSERT OR IGNORE INTO anomalies (log_date, log_file, entry_time, exit_time, car_number, fee, is_suspicious, dedup_key, status) VALUES (?, ?, ?, ?, ?, ?, ?, ?, 0)",
  "params": ["2026-08-22", "system.2026-08-22.log", "2026-08-22 21:07:12", "2026-08-22 21:07:12", "川ABA0530", 23.0, 0, "<sha256hex>"]
}
```

- 批量插入：把多条记录合并为一次请求（响应中 `result[0].changes` 可判断实际插入行数），控制请求次数。
- 建表请求同样走该端点，工具在每次上传会话开始时先发一次 `CREATE TABLE IF NOT EXISTS`（幂等）。
- 响应判断：HTTP 200 且 JSON `success == true` 视为成功；否则按 `errors` 内容给出可读错误（Token 无效 / 库不存在 / 网络失败分开提示）。
- 免费额度参考（当前量级远够）：D1 每天 10 万行写入 / 500 万行读取 / 5GB 存储；Workers（非本仓库使用）每天 10 万请求。
